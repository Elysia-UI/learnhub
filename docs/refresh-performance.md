# 刷新速度优化实测

日期：2026-10-28。本轮针对刷新等待时间，不开展全项目验收，不更改页面设计或业务数据。

## 原因与实现

原 bootstrap 数据读取在管理员场景需要执行 27 条 SQL，多个查询通过连接池分批访问云数据库；取回数据后另查未读数量。刷新完成前，前端会等待这次数据读取。

现在使用 MySQL 8 的 CTE 和 JSON 聚合，将同一批数据与未读数量合并为一条参数化只读语句。数据库返回压缩内容，由后端解压后交给原 DTO，浏览器收到的字段和业务内容保留。管理员样本数据库压缩包约 84.6 KB，最终状态 JSON 约 275.1 KB。没有启用多语句查询，没有增加跨用户缓存，响应使用 `private, no-store`；每次刷新仍然查询数据库。

相关实现：`server/services/snapshot-read.mjs`、`server/services/snapshot.mjs`、`server/app.mjs`。独立列表和详情接口继续使用现有查询方式。

## 同一连接池的新旧实现交替测量

管理员角色，按旧、新顺序各执行三次；计时覆盖数据库读取与 DTO，未包含浏览器绘制。

| 样本 |  优化前 | 优化后 |
| ---- | ------: | -----: |
| 1    | 1175 ms | 725 ms |
| 2    |  857 ms | 488 ms |
| 3    |  636 ms | 402 ms |

中位数从 857 ms 降至 488 ms，下降约 43%。这些样本返回相同的 114 篇帖子、366 条评论和 20 门课程，最终状态 JSON 同为 275131 字节。不是通过减少内容得到提速。

## 实际运行服务测量

通过 `http://127.0.0.1:5173/api/bootstrap` 完整读取游客 HTTP 响应：

- 优化前四次：913、1148、446、764 ms。
- 重启新版服务后第一次：1438 ms。
- 随后四次：577、457、601、649 ms，全部 HTTP 200。
- 同一浏览器管理员刷新观察：bootstrap 收到响应头由 955 ms 降至 624 ms。页面展示、静态文件和浏览器绘制另计，不能把接口耗时当作整页加载时间。

当前公网云数据库仍有网络波动，服务刚启动、首次建立连接或准备查询时仍会较慢。本轮没有进行并发压力或长期性能测试。

## 内容、权限与回归

- 对游客、普通用户、教师、管理员四种角色，将新旧读取结果递归比较：17 个状态分区的字段及关联内容一致。关系数组按内容归一化后比较，排序由显式日期、置顶及章节位置恢复。
- 核对教师时发现历史积分演示数据有 50 条 MySQL 零日期，原日期格式化会抛错、中断刷新。现已对无效日期返回空值，保留记录及积分，不编造历史时间。上述四角色比较使用同一日期保护函数；日期问题不计入速度提升。
- 新增接口断言：待审帖子对游客和其他用户隐藏，作者及管理员可见；通知、课程报名、签到、积分、浏览历史和 AI 会话仅属于当前用户；普通用户不能读取管理员日志；未读总数与 SQL 一致；新评论经 bootstrap 重新读取可见。
- `npm test`：前端 14/14、真实 HTTP + 云 MySQL 19/19，失败 0；接口部分约 94.26 秒。AI 测试使用本地协议服务，未在本轮重新调用付费模型。测试中的预期失败响应不属于失败用例。
- `npm run build`：TypeScript 与 Vite 构建通过，Vite 耗时 6.16 秒。
- 浏览器首页刷新后正常显示，检查到的控制台错误和警告为 0。
